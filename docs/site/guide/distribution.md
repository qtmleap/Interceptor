# 配布と更新

::: info 開発中のプレビュー
配布形式は現在のアプリで実装されています。ただしアプリが行うのは取り込みまでで、取り込んだリビジョンは無効のままです。実際の通信での実行や送信はまだありません。
:::

プラグインを配布するリポジトリは静的なHTTPSの `repository.json` 1つと、その隣に置くパッケージファイルでできています。`repository.json` は、パッケージの一覧データなどを収めた配布用ファイルです。GitHub Pages、raw GitHub、自前のサーバーなど、静的配信できればどこでも使えます。アプリはHTTPSで取得するため、リポジトリの追加にgit cloneやAPIトークンは不要です。

## 前提条件

パッケージの作成、署名鍵の生成、配布用JSONの生成はBunで行えます。**Xcode、Swift、アプリ本体のソースコードは必要ありません。** コマンド例はmacOS/Linuxのシェル向けです。動作確認にはmacOSとBun 1.4.2を使っています。Bunの準備とパッケージの作成は[はじめての作成](/guide/getting-started.md)を参照してください。

このガイドに付属する [repository.tsをダウンロード](/tools/repository.ts)し、`my-first-plugin.json` と同じ作業フォルダに保存してください。以降のコマンドはその作業フォルダで実行します。

```sh
bun repository.ts --help
```

このBunの例は配布情報を生成するためのものです。アプリのマニフェスト検証をすべて複製してはいません。**配布するパッケージは先にアプリへ取り込んで合成テストを行ってください。** プラグインのソースを実行したり、ファイルをアップロードしたりする機能はありません。

## レイアウト

```text
my-first-plugin/
  build.ts                 パッケージを作るためのファイル
  plugin-id.txt            プラグインのUUIDを保存
  my-first-plugin.json     作成したパッケージ
  repository.ts            ダウンロードした生成スクリプト
  repository-id.txt        リポジトリのUUIDを保存
  my-repo/                 公開するのは、この中身だけ
    plugins/first.json     パッケージのコピー
    repository.json        生成物
```

## 公開手順

まず、公開するファイルの置き場を作り、テスト済みパッケージをコピーします。

```sh
mkdir -p my-repo/plugins
cp my-first-plugin.json my-repo/plugins/first.json
```

`plugins/` にはパッケージJSONだけを置きます。最大100件で、ファイル名は英数字・ドット・ハイフン・アンダースコアからなる `.json` にします。隠しファイルやシンボリックリンクは使えません。

初回だけ、自分の署名鍵とリポジトリのUUIDを作ります。次のUUID生成コマンドは、ファイルがすでにある場合は何もしません。

```sh
mkdir -p ~/.config/interceptor
bun repository.ts keygen ~/.config/interceptor/my-plugins.pem
bun -e 'const p = Bun.file("repository-id.txt"); if (!(await p.exists())) await Bun.write(p, crypto.randomUUID() + "\n")'
```

`keygen` は秘密鍵をPKCS8 PEM形式、ファイル権限0600で保存します。既存の鍵は上書きしません。画面に表示するのは公開鍵のフィンガープリントだけです。表示された64文字のフィンガープリントを控えてください。後で、利用者が署名鍵を照合できるよう、別の信頼できる経路で伝えます。`publish` の成功時にも同じ値が表示されます。秘密鍵はGit管理外かつ公開フォルダの外に保管し、別の安全な場所にもバックアップしてください。このPEM形式は、アプリ開発用のSwift製CLIが使う32バイトの生の秘密鍵とは異なります。

次のコマンドで `repository.json` を生成します。`$(cat repository-id.txt)` は、保存したリポジトリのUUIDを読み込むシェルの記法です。

```sh
bun repository.ts publish my-repo \
  --id "$(cat repository-id.txt)" --name "My repository" --sequence 1 \
  --key ~/.config/interceptor/my-plugins.pem
```

- 成功すると `my-repo/repository.json` ができ、生成先・更新番号・パッケージ数とフィンガープリントが表示されます。
- このBunの例では `--key` は必須で、署名付きの配布情報だけを生成します。
- メタデータの有効期限は30日です。アプリが受け付ける有効期間の上限は90日です。期限が切れる前に、更新番号 `--sequence` を増やして再生成し、再配置してください。
- 秘密鍵と、期限付きの `repository.json` はGitにコミットしないでください。公開時のビルド手順で生成します。

次に `my-repo/` の中身だけを静的HTTPSサイトへ配置します。たとえば公開先が `https://example.com/interceptor/` なら、次の2つのURLでファイルを取得できるようにします。配置操作は利用するホスティングサービスの手順に従ってください。

- `https://example.com/interceptor/repository.json`
- `https://example.com/interceptor/plugins/first.json`

利用者はアプリの「設定」→「プラグイン」→「＋」→「リポジトリを追加」で、`repository.json` のHTTPS URLを入力し、「プレビュー」を押します。署名鍵の確認は下の「整合性と信頼」に従ってください。追加したリポジトリからスクリプトを開き、ソースを確認して「無効状態で取り込む」を押します。取り込んだ後のテスト手順は[はじめての作成](/guide/getting-started.md#_4-取り込みとドライラン)と同じです。

## 形式の概要

署名するのはリポジトリの配布情報です。個々のパッケージはその配布情報に記載されたSHA-256とサイズで照合します。Appleのアプリ署名や公証とは別の仕組みです。

### エンベロープ

`repository.json` の外側の形式です。`payload` には、次の「インデックス」をbase64で文字列にしたものが入ります。Bunのスクリプトがこの変換と署名を行うため、通常は手作業で組み立てません。

```json
{"schemaVersion":1,"payload":"<インデックスJSONのbase64>","signature":{"algorithm":"ed25519","publicKey":"<base64 32バイト>","value":"<base64 64バイト>"}}
```

形式上は `signature` を省略できますが、このガイドの生成例は署名を必須にしています。署名の対象は `InterceptorRepository/v1`、NULバイト、デコード後のpayloadの正確なバイト列です。JSONの正規化はしません。

### インデックス

`schemaVersion`、`id`（UUID）、`name`、`sequence`（1〜2^53−1）、`issuedAt`、`expiresAt`（UTCの秒単位）、`plugins`（最大100件）。各プラグインは `id`、`name`、`version`、`packagePath`（`plugins/<file>`）、`sha256`、`size`（パッケージの正確なバイト列）を持ちます。

### アプリ側の検証

アプリは、パッケージの SHA-256、サイズ、`id`、`name`、`version` がインデックスの記載と合うかを検証します。ほかにも次を確認します。

- 期限切れのメタデータは拒否されます。
- `sequence` が下がる（ロールバック）か、同じ `sequence` で内容が違うものは拒否されます。

## 整合性と信頼

フィンガープリントは公開鍵を識別する64文字の値です。「鍵を固定する」とは照合した公開鍵を、以後の更新を検証する基準としてアプリに保存することです。

- ハッシュでできるのは、インデックスと食い違うパッケージの検出だけです。署名のないサーバーを制御する人は、パッケージとインデックスの両方を差し替えられます。
- 署名のあるリポジトリでも、初めて見た鍵は**未検証**です。公開者はフィンガープリントをリポジトリとは別の信頼できる経路で伝えてください。署名はプラグインの安全性や公開者の本人確認を保証しません。
- 署名なしのリポジトリはアプリでは警告を確認すれば追加できますが、常に未検証と表示されます。
- 固定済みの鍵が変わる、署名が消える、署名やハッシュが合わない、ダウングレードやロールバックがあるといった場合、更新は拒否されます。**鍵のローテーションは未実装です。**

初めて署名付きリポジトリを追加するときは、画面に表示される公開鍵のフィンガープリントを、公開者から別の信頼できる経路で入手した値と比較します。一致を確かめたら、別の経路で入手した64文字を入力欄に入れ、「公開鍵を照合して追加」を押します。追加済みの未検証リポジトリではリポジトリ詳細画面の「公開鍵を照合」を使います。値が一致しない場合は、固定せず追加・更新を中止してください。

## 更新

同じプラグインを更新するときは、`plugin-id.txt` を残し、`version` を上げてパッケージを再生成します。内容が変わると、別のリビジョンになります。更新後のリビジョンも無効なまま保存され、自動では実行されません。現在、実行許可（グラント）の機能はありません。

配布する側は `my-repo/plugins/first.json` を新しいパッケージで置き換え、同じ `repository-id.txt` と署名鍵を使って再び `publish` します。初回が `--sequence 1` なら、次は `--sequence 2` にします。この番号は配布情報の更新順を示し、古い情報への巻き戻りをアプリが検出するために使います。生成した `repository.json` とパッケージを、両方とも公開先へ配置してください。
