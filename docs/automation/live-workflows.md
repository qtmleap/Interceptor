# Live script workflows

Proposed implementation contract, 2026-10-18, with independent plan-review resolutions. This extends the implemented [repository/runtime foundation](repository-runtime-foundation.md); that v1 preview remains compatible and performs no network I/O. User scope: TypeScript templates and reusable utilities; reuse captured semantic request headers for another API on the same origin, project its response, and deliver a selected result to a configured endpoint. Each installed revision supports Off, Notify and Run, and Automatic. A notification opens a pending-run review. Its Run action authorizes the complete displayed workflow; no second response approval is assumed. Automatic mode consumes the same frozen workflow without the pending-review step. This document specifies intended behavior, not completed implementation.

## Execution boundary and compatibility

One operation performs at most one same-origin API request and zero or one external delivery. External sending is optional plugin behavior, never a universal prerequisite or destination field. One fresh bounded QuickJS planning invocation returns a native request intent; native HTTP performs it; one fresh fixed onHTTPResult invocation transforms the approved response into a webhook intent. Both invocations retain the existing 50 ms deadline, 8 MiB heap and 256 KiB stack budgets. No general network API, persistent VM, timers, module loader or promise jobs are added. Import, refresh, edit and preview do not activate a workflow or send traffic.

The v1 JavaScriptHook enum, ScriptRunning API, two-hook preview behavior, C result validator and v1 input/result byte limits remain unchanged. Add a separate workflow-stage API and strict v2 validators for planning and HTTP-result stages, including separate native C entry points or an explicit v2 validation path; do not relax the v1 validator to accept new actions. Each operation/stage receives its own lifetime-safe cancellation token. Disabling one workflow or leaving one screen cancels only owned operations; it must not call the legacy executor's global cancel method on an unrelated run.

## Capture adapter and dependency direction

Mudmouth exposes an optional neutral, Sendable lifecycle event sink, default nil, with a synchronous try-offer admission method returning accepted/rejected. The sink cannot await JS, HTTP or disk, create unbounded Tasks, or block the NIO forwarding event loop. A full or contended bounded queue rejects admission and records a reason counter. The existing transfer path continues with a nil sink or a rejected event.

Freeze neutral public Mudmouth types independently of Automation: CaptureLifecycleEvent contains an immutable request snapshot plus optional response snapshot, a four-case phase enum (request.headers, request.completed, response.headers, response.completed), eventID/exchangeID/time, request method and optional response status, verified HTTPS authority (normalized DNS host/effective port), encoded target, ordered HeaderField(name,value) entries and absent/complete/truncated/unavailable body state. CaptureLifecycleSink is an @Sendable synchronous (CaptureLifecycleEvent) -> Bool admission closure. MITM.startTunnel(..., eventSink: ... = nil) passes that sink and connection-scoped verified authority to ProxyHandler. Values contain no NIO channel/context/ByteBuffer, SwiftData reference, script, grant, endpoint or app authorization type. Request head/end events do not depend on receiving an origin response; response phases retain original request context. Body state distinguishes absent, complete, truncated and unavailable. Initial budgets: headers/path 8 KiB each, body encoded/decoded 32 KiB each, admission queue 32; automatic events awaiting planning expire after five seconds. Oversize or incomplete data never masquerades as a complete body.

For the initial HTTPS capture path, carry validated CONNECT authority into ProxyHandler, accepting the existing HTTPS/443 capture scope and rejecting conflicting, duplicated or missing inner Host values for automation admission. Generic Record dictionaries and legacy saved captures lack the required authority and duplicate-header fidelity. Do not reconstruct authenticated execution snapshots from them. Keep old record viewing compatible.

PacketTunnel/AutomationCaptureAdapter imports Mudmouth and AutomationCore, converts neutral snapshots to Core value DTOs, and offers them to the bounded workflow queue. It owns both dependencies and revalidates snapshot bounds/authority and grants at the integration boundary. The new HTTP-result stage is not a case added to PluginSubscription.Phase. The standalone InterceptorAutomation package and its Core, Runtime, Storage and Transport targets must not import or depend on Mudmouth. Mudmouth must not depend on InterceptorAutomation. PacketTunnel wires the sink at tunnel startup and stops its owned worker on tunnel stop or consent withdrawal.

## v2 manifest and request scope

Add strict manifest schemaVersion 2, preserving v1 decoding and exact distribution-envelope semantics. Existing identity/name/version/subscriptions/read/endpointBindings/settings fields remain. A required workflow declares permitted same-origin methods and exact/prefix paths, native header inheritance (allEndToEnd or named headers), and API-response read projection. An optional endpointBinding declares external delivery only when that plugin uses it. Declarations do not grant access. Activation separately approves captured-data reads, native inherited-header use, target method/path scopes, response reads and optional export to exactly one endpoint revision. Settings revision, mode and revocation epoch are part of that activation. Import remains inactive. Source edits, package updates and expanded settings/permissions never inherit a prior grant.

Additional manifest field (endpointBinding is optional; all other keys shown are required except names in the alternative named-header mode):

    {"workflow":{"endpointBinding":"result","sameOrigin":{"methods":["GET"],"paths":[{"kind":"exact","value":"/api/account"}],"inheritHeaders":{"mode":"allEndToEnd"}},"responseRead":{"metadata":["status"],"headers":[],"queryKeys":[],"body":{"mode":"jsonPointers","pointers":["/data"]}}}}

The alternative inheritance object is {"mode":"names","names":["authorization","cookie"]}. Names use the existing bounded header-name validator; duplicates are rejected case-insensitively. The declaration allEndToEnd requests the native policy-filtered end-to-end set. Its activation explicitly approves that policy, including authentication headers and future captured end-to-end names; named-header mode instead freezes a case-insensitive allowlist. The review states which scope is being approved. Native inheritance permission is independent of a JavaScript header-read grant. Reading no headers in JS does not prevent separately approved native forwarding, and granting a JS read does not authorize forwarding.

ResponseRead uses the existing read-declaration shape but permits only status metadata and an empty queryKeys array. Methods and paths each contain 1–8 distinct entries; when endpointBinding exists, it is the sole endpointBindings entry; when absent, endpointBindings must be empty and no external-delivery grant or configuration is required. Header/query name and body-pointer counts retain existing declaration caps.

A plugin without external delivery may use onHTTPResult to process an approved API response and return actions:[]; no endpoint must be invented to enable it. An empty planning action list also completes without network side effects.

One shared AutomationCore canonicalization helper validates manifest scopes, grant scopes and final intent targets. Target paths are ASCII, start with exactly one slash, contain no query/fragment/user info or absolute/network-path URL, and are at most 1,024 encoded bytes. Validate every escape, canonicalize hexadecimal escapes to uppercase, decode percent-encoded unreserved characters once, and reject literal/encoded backslashes, encoded slashes, dot or dot-dot segments, empty interior segments, controls/NUL, and all encoded percent signs (%25), preventing a second decoding interpretation. Reject malformed UTF-8 escape sequences and any alternate encoding whose canonical form is ambiguous. Canonical paths are the representation persisted and displayed for approval. Prefix matching is segment-boundary matching: /api matches /api and /api/account, not /apix; root / matches any accepted path. Trailing-slash behavior is explicit: preserve it; a prefix ending in / matches itself and strings starting with that prefix, but not the same path without its trailing slash. Exact matches preserve the trailing-slash distinction.

Compare the final normalized method and canonical path against BOTH manifest and frozen grant immediately before native dispatch. Methods are upper-case validated tokens; reject CONNECT, TRACE and upgrades. The trusted HTTPS scheme, normalized DNS host and effective port come only from the capture authority, never the script or a Host header override. Query pairs are a separate native-encoded field, preserve order/duplicates, and do not alter origin or path scope. Redirects are rejected, including same-origin redirects, in this initial version.

## Stage types, projections and byte limits

Planning hooks retain onRequest(event, config)/onResponse(event, config) according to subscription direction, but run through the separate v2 stage API. The fixed result signature is onHTTPResult(event, config). Both stages receive the same frozen config bytes with exactly {"settings": frozenSettingsObject, "endpoints": {bindingName: canonicalUUIDString}}. The endpoints object is empty when no external-delivery binding is declared; otherwise it contains the sole granted binding. Existing settings limits remain 8 KiB/depth 16; the v2 aggregate config limit is 16 KiB including wrapper/endpoint overhead. Native credentials, origin capabilities and inheritance snapshots are never config fields. An authored result hook reads config.endpoints.result rather than hardcoding a destination UUID. A planning result is {"actions":[]} or exactly one sameOrigin action:

    {"actions":[{"type":"sameOrigin","method":"GET","path":"/api/account","query":[{"name":"view","value":"summary"}],"continuation":{"label":"Account"}}]}

Only type/method/path are required action fields. Optional query contains at most 32 ordered name/value string pairs, each value a string or null for a valueless item, with at most 8 KiB of native percent-encoded query and at most 8 KiB of serialized pair data. Native code percent-encodes name/value components; a supplied ampersand, equals sign, slash or percent cannot create another component. Path contains no query or fragment.

Optional body is either {"mode":"json","value":JSONValue} or {"mode":"raw","base64":"...","contentType":"application/octet-stream"}. Raw base64 is canonical padded RFC4648; decoded body and final wire body are each capped at 32 KiB. JSON is serialized natively once and the resulting UTF-8 wire bytes must fit 32 KiB. Body absence means none; GET/HEAD forbid a supplied body. Raw contentType is a validated bounded media-type string with no controls or line breaks. Optional continuation is a JSON object capped at 8 KiB/depth 16 and contains only data already available to the planning script. The native header snapshot/capability is never inserted into continuation or exposed through an arbitrary script-provided inheritance handle.

V2 planning input is a strict event object with id, exchangeID, phase, time, request and response only for an original response subscription. Projection omits every ungranted field. Request may contain approved method/host/path, headers, query and body; response may contain approved status/headers/body. The ordering and body representation are normative:

- Headers are an ordered array of {"name":"lower-case-token","value":"exact semantic value"} entries, preserving duplicate end-to-end entries. The UTF-8 JSON array is capped at 8 KiB; do not merge generic fields with semicolons.
- Query is an ordered array of {"name":"name","value":"string"} or {"name":"flag","value":null}, preserving duplicate names and valueless items. Apply the name allowlist before exposing it; serialized and encoded query caps are each 8 KiB.
- If body read is not granted or mode is none, omit body. If granted and no body exists, use {"state":"absent"}.
- A complete raw projection is {"state":"complete","mode":"raw","base64":"..."}. A complete pointer projection is {"state":"complete","mode":"jsonPointers","values":[{"pointer":"/data","found":true,"value":JSONValue},{"pointer":"/missing","found":false}]}. Values follow declared pointer order; found=false forbids value. Do not treat a missing pointer as a JSON null value.
- An incomplete captured body is {"state":"truncated"}, with no partial bytes or projected values. Unavailable projection is {"state":"unavailable","reason":"notCaptured"}, with reason restricted to notCaptured, unsupportedEncoding, invalidJSON or decodeLimit. It carries no bytes/values. No body getter may perform an unbounded decode.

The fixed result hook receives exactly operationID, eventID, exchangeID, phase="http.result", time, the frozen approved original request projection, the approved API response projection, and optional frozen continuation. Response uses the status/headers/body shapes above; it contains no arbitrary origin credentials or implicit original-request fields. Extra keys are rejected. Planning event and result input JSON have depth at most 64. All JSON parsing, projection and byte caps apply before admission to JS.

Freeze separate v2 envelope caps: planning input and HTTP-result input each 192 KiB; planning output 96 KiB/depth 32; HTTP-result output 32 KiB/depth 32; continuation 8 KiB/depth 16. A 32 KiB raw body needs 43,692 base64 characters, so a planning intent with body/query/continuation cannot use the v1 32 KiB result cap. These envelope caps include all keys/escaping; smaller component limits still apply. Capture/read bodies remain 32 KiB encoded and decoded. No v1 constant is changed to achieve these limits. Each v2 stage must have just-below/at/above-limit tests, including maximum-size base64 body and a result input containing both request and response projections.

The native API outcome is either a complete HTTP response or a transport failure. DNS/TCP/TLS errors, deadline/cancellation, malformed/incomplete HTTP framing, incomplete bodies, or encoded/decoded response-limit overflow terminate the operation without result JS. A fully received HTTP 401 or 500 is still an HTTP response and enters normal approved projection/result processing. A complete response whose requested JSON projection cannot be decoded is represented as unavailable/invalidJSON; it is not reported as a transport failure or a successful complete JSON body. HEAD/204/304/no-body responses use correct HTTP framing semantics and absent body. Never manufacture completion after early EOF or treat partial JSON as a complete response.

OnHTTPResult returns {"actions":[]} or exactly one existing-shaped {"type":"webhook","endpointId":UUID,"json":JSONValue} action, validated by the separate v2 result validator against the optional one granted endpoint. Without an external-delivery binding, only actions:[] is accepted; same-origin processing still completes normally. No sameOrigin action, callback name, URL or chain is allowed at this stage.

## Deterministic native header inheritance

Apply this ordered policy to a bounded immutable original header-pair snapshot; compare names case-insensitively and preserve the original relative order of retained end-to-end entries:

1. Validate token names and semantic values; reject CR/LF/NUL and invalid values. Validate Host against trusted CONNECT authority. Missing/duplicate/conflicting Host rejects automation admission. For a selected Authorization singleton, conflicting duplicate values reject the operation; identical duplicates collapse to the first entry. No arbitrary dictionary merge resolves a conflict.
2. Read every original Connection value before filtering and collect its valid connection-option tokens. A malformed Connection token list rejects automation admission rather than guessing a filter. This check does not expose those values to JS.
3. Select only headers requested by the manifest's inheritance mode and approved by the frozen native-forwarding grant. A JavaScript read grant alone does not add any header. AllEndToEnd requires an explicit allEndToEnd activation; a narrower named grant intersects the selected names.
4. Remove Connection and every Connection-nominated field, Keep-Alive, Proxy-Connection, Proxy-Authenticate, Proxy-Authorization, TE, Trailer, Transfer-Encoding, Upgrade, Host and transport/pseudo-header framing. These exclusions cannot be overridden by a grant.
5. For no body or a replaced body, remove ALL body-dependent fields: Content-Encoding, Content-Length, Content-Type, Content-MD5, Digest, Content-Digest, Repr-Digest, Transfer-Encoding, Trailer and Expect. Initial intents can supply only no body or a new JSON/raw body, so this removal always applies. Do not retain a captured digest or content encoding for newly serialized bytes. Do not inherit the original operation's Idempotency-Key for a different request.
6. Generate Host from the trusted origin and framing from the final method/body. A supplied JSON body gets application/json; a raw body gets its validated explicit contentType; no body gets no inherited Content-Type/Encoding/Digest. The transport generates the correct body length and HTTP framing; the script cannot replace them. Recheck final header and body budgets after generation.

Authorization/Cookie inheritance stays native even if JS cannot read those fields. Other approved duplicate end-to-end entries remain ordered pairs. External delivery never receives inherited origin credentials; its credentials come only from the configured endpoint revision. Copied path-bound signatures or expired credentials may fail; show their actual HTTP result accurately.

## Header visibility and external transport privacy

External transport ALWAYS creates a fresh endpoint-owned header set: no captured original-request, original-response or additional-API response header is inherited into external HTTP headers. Only native required transport fields, Idempotency-Key and independently configured endpoint credentials are allowed. Scripts cannot supply arbitrary external header fields. This rule is unconditional and not a toggle.

A separate per-installed-revision native preference, headersVisibleToScript, defaults to false. Apply it to all JS event projections, including original request/response and the additional API response: when false, omit header fields even when the manifest declares header reads. When true, expose only the intersection of manifest-declared names and the activation's approved JS-read names. Changing it invalidates old pending work and requires the corresponding activation update; it never edits the immutable package, host, path or method. Existing body projection permissions are independent.

Label the UI "ヘッダー情報をスクリプトに渡す", not "ヘッダー情報を送信しない": once JS can read values, it can embed them into a JSON payload. Body read/export permissions do not imply header-read permission. Native same-origin authentication inheritance remains available independently, without exposing Authorization/Cookie or other values to JS. No promise is made that permitted response bodies cannot themselves contain sensitive data.

## Activation and frozen execution plans

Keep installation/trust data separate from a versioned App Group SQLite operational store. Activation atomically stores the exact verified immutable package bytes, encrypted in shared state, together with their SHA-256 revision, repository/local provenance, grant ID/epoch, captured-data scope, forwarding scope, method/path scope, response scope, settings revision/mode and endpoint ID/revision/epoch. Verify package bytes and their digest before staging; encrypt using authenticated associated data binding the revision and activation IDs; commit the encrypted blob and activation record together. A key/preparation failure creates no active grant. A replacement activation invalidates the previous epoch in the same transaction.

The extension NEVER reads the app-private catalog or follows an app-private file path. It reads the shared activation snapshot, decrypts it, checks the exact package-byte digest and strict schema, and uses only that immutable package/settings revision. Provider IPC contains versioned operation IDs, activation IDs, expected plan digests and epochs only, not package bytes, captured secrets, credentials or paths. The store is authoritative. Import stays inactive until this separate explicit activation.

For Notify and Run, execute the planner ONCE before creating a pending-review item. Validate its result and freeze a native plan containing operation/event/exchange IDs, exact validated intent and native wire request representation, continuation, approved request projection, separate authorized native header snapshot, exact shared package revision, grant/activation/settings/endpoint revisions and epochs, mode and createdAt/expiresAt. Encode these frozen payload fields once; store their digest separately as authenticated record metadata, outside the bytes being hashed. Commit encrypted payload and digest as one durable record. Generate the digest over domain "InterceptorFrozenPlan/v2" plus NUL plus those exact encoded payload bytes. Verify those bytes/digest on every consume; do not re-serialize mutable current settings to reconstruct a plan. Display review from the same frozen record.

Notify only after pendingReview is durably committed. A notification contains only a job ID; tapping it does not approve or execute. Run supplies the displayed operation ID, plan digest and expected epoch and performs one compare-and-swap from pendingReview to approved. It consumes that exact plan once, does not run JS planning again, does not fetch a new source/configuration, and rejects expired, changed, revoked or missing revisions. Repeated taps return current status rather than creating another operation. Automatic uses the SAME frozen-plan preparation, persistence, scope validation and approval transition, without a pending-review/user-tap step.

Only the PacketTunnel service performs live side effects, including manual runs requested from the app. The app never starts a second sender. A stopped tunnel gives restart guidance. Requesting Run does not silently restart capture or replace old credentials with a newer capture.

## Durable states, ownership and recovery

Each captured event/revision/grant binding has one durable operation ID and uniqueness key. Duplicate event admission or duplicate IPC references the same operation. Every transition is a transactional compare-and-swap on operation ID, expected state, expected grant/settings epochs and endpoint epoch when present, and plan digest when present; a single lease/owner/session token identifies the worker. Invalid/expired epochs and deadlines transition to terminal without issuing a new side-effect permit.

| From | Transition and atomic data | Recovery / repeated request |
| --- | --- | --- |
| New | Insert planning marker before invoking JS, with immutable activation/package identity and captured projection/snapshot. | Duplicate admission returns the existing operation. Interrupted planning becomes terminal/quarantined; do not replan it. |
| planning | After one valid planner result, atomically persist frozen bytes/digest and move to pendingReview (Notify and Run) or approved (Automatic). Empty action/failure becomes terminal. | No notification exists before pendingReview commits. |
| pendingReview | Run with matching digest/epoch CASes once to approved; cancel/expiry/revocation becomes terminal. | Recovery may redisplay the same unexpired plan. Duplicate taps never start another planner/request. |
| approved | Recheck final method/path/header/body/grant/endpoint scope, persist apiInFlight marker BEFORE starting native network I/O. | Recovery can resume an approved operation only if no apiInFlight marker was committed; acquire one permit by CAS. |
| apiInFlight | One complete HTTP response and its approved response projection are atomically committed as resultReady with resultInvocationStarted=false. Transport/limit failure becomes terminal. | Recovery of apiInFlight without a durable complete response is terminal/unknownOutcome, even for GET; NEVER replay the API call. |
| resultReady | CAS resultInvocationStarted from false to true before one onHTTPResult invocation, using frozen package/request/continuation and durable response. Atomically commit a valid nonempty delivery record and deliveryQueued, or terminal for no-action/failure. | An interrupted started result invocation is terminal/quarantined, not rerun. An unstarted resultReady may be claimed once. |
| deliveryQueued | Outbox CAS claims one bounded attempt/lease. Success, permanent failure, revocation or TTL becomes terminal; eligible transient failure persists next-attempt time under the same operation/delivery identity. | An uncertain webhook attempt may retry only the immutable recorded delivery; it must never repeat API fetching or result JS. |
| terminal | Persist bounded outcome/reason only; no transition back to an executable state. | A user's new explicit execution, if offered later, is a separate new operation requiring a new review; not a hidden retry. |

Prepare first API request bytes from the frozen validated intent/header snapshot, and compare against both frozen manifest and grant immediately before the apiInFlight permit. Recheck activation/endpoint epochs again before each network stage/attempt. Disable, consent withdrawal, edits, endpoint/capture-host removal and revocation invalidate pending work and cancel only owned network and JS tokens. Already transmitted bytes cannot be recalled; cancellation of in-flight effects is best effort. No automatic retry of an uncertain same-origin API call is allowed.

## Protected storage and immutable delivery

Tables cover shared encrypted package activations, epochs, frozen plans, pending runs, response/result markers, outbox leases and bounded history. Encrypt sensitive blobs with per-grant AES-GCM keys in device-only shared Keychain; authenticate operation/revision/epoch/digest identifiers as associated data. Apply backup exclusion and first-unlock file protection to DB/WAL/SHM. Verify actual app/extension key access and locked-startup behavior on device before readiness claims.

Pending-review storage is bounded to 32 items/2 MiB/15 minutes. It includes the encrypted frozen request/continuation/projection/snapshot and package reference; a separately deduplicated encrypted package blob is accounted for in the operational store's disk budget. Never evict a still-executable item without transitioning it to terminal. Notification denial leaves in-app access. History retains at most 1,000 entries/seven days with IDs/time/status/reason only, not bodies, credentials or secret paths/query.

When the result action is accepted, serialize its JSON payload exactly ONCE into UTF-8 bytes. Atomically create one delivery UUID and immutable record: operation ID, delivery ID, package/grant/settings identity and epochs, exact endpoint ID/revision/epoch and credential revision, POST/application-json transport metadata, exact payload bytes, payload SHA-256/size, createdAt and expiry. The endpoint revision identifies an immutable encrypted URL/credential snapshot; retries never substitute a newly edited destination or credential. Endpoint edits invalidate old work instead.

Send the canonical UUID string in the Idempotency-Key HTTP header. Generate it once in the deliveryQueued transaction; every retry uses the same UUID header value, endpoint revision and exact payload bytes. A transport adapter must receive these fields explicitly and cannot recompute a key from attempt count/time or re-serialize payload objects. Receiver support is needed to suppress duplicate effects; no exactly-once claim.

Outbox limits: 256 entries/8 MiB, bounded total disk budget; two network attempts concurrently, ten-second per-attempt deadline. All stages/attempts consume bounded worker capacity; each same-origin API dispatch and each initial/retried external delivery attempt consumes the same shared rate buckets (plugin 10/min burst 2, global 60/min burst 4). Acquire the API rate permit before the apiInFlight CAS, so local-only/no-action-result plugins cannot bypass sustained request limits; quota denial defers an unstarted approved plan only until its expiry. External attempts use those same buckets, with fair scheduling and bounded CPU accounting. Webhooks have at most five total attempts with 5/30/120/600 second bounded jitter and a 15-minute TTL. Retry transient transport errors/408/429/5xx; refuse redirects, permanent 4xx and TLS/policy failures. API fetch is never included in this retry policy.

Direct native egress and trusted connection provenance exclude all workflow traffic from capture; a spoofable HTTP marker never grants exclusion. API responses enter only the result-stage path and cannot generate capture admission or another same-origin request. Verify actual device routing/DNS aliases and app-closed execution.

## Authoring and UI

Keep Bun and readable deterministic emitted JavaScript. Initially supply self-contained TypeScript helpers/templates; ambient declarations alone do not implement helpers. A shared helper prelude or local-module bundling needs its own deterministic compiler contract and emitted-code tests. Publish live templates only after a compatible native runtime exists; current v1 samples and signed feed remain usable.

Reuse native navigation/forms/toolbars and OK green, WARN yellow, ERROR red. The basic per-script screen shows host, path and method read-only from the immutable plugin manifest, with no disclosure chevrons or editing routes. Execution mode and the separate header-visibility preference can change there; neither can rewrite the plugin capture conditions. Plugin behavior determines additional permissions. Show an endpoint only for a plugin declaring external sending, in its relevant permission/configuration flow; do not show a destination for local-only plugins. Add conditional permission review, pending-run review and status history. Review displays the frozen target/method, approved inherited header names, body/source revision, destination identity and expiry; redact secrets without concealing which scopes were granted. Run approves that complete workflow, including result projection/delivery, without a second response approval. No custom OS-specific round toolbar button styling. New screen/component mocks precede UI code; a human selects them in Mock Diff Viewer, then native iPhone/iPad en/ja light/dark captures are compared. Mocks remain proposals until selected. Standard text size follows the user's scope.
